# Nightly Training Pipeline — Audit (Phase 1)

_Audited 2026-06-26 · branch `claude/mcts-training-audit-zjsqe6` · state at generation 102, run `20260625T212027Z`._

This document maps how the current nightly training works and answers the Phase‑1
questions, with file:line evidence. The companion diagnosis (root causes + fixes)
is in [`training_diagnosis.md`](training_diagnosis.md).

## How the nightly run works (end to end)

Entry point: `training/nightly_run.py::run()` (invoked by `python -m training.nightly_run`).
Orchestrated by GitHub Actions `.github/workflows/nightly-mcts-training.yml` every 6 h
(`cron: "0 */6 * * *"`, `timeout-minutes: 350`), command:

```
python -m training.nightly_run --hours 5 --games-per-arena 12 --resume training/state/latest.json
```

Steps inside `run()`:
1. Load durable state — `state_store.load_latest/​load_champion`, `ratings_db.connect`
   (`nightly_run.py:170-181`). Cold start seeds the champion from
   `config/key_findings_best_params.json` (`_seed_champion_params_from_config`, `:63`).
2. **Self‑play generation loop** (`:196-298`) — time‑budgeted to 70 % of the wall‑clock
   budget (`_GENERATION_BUDGET_FRACTION = 0.7`, `:44`). Each generation plays
   champion vs 3 rotating challengers via `selfplay_core.run_generation` and persists
   state atomically.
3. **Candidate generation + evaluation** (`:300-347`) — `selfplay_core.build_candidate`
   then `selfplay_core.evaluate_candidate`, gated on `time.monotonic() < deadline`.
4. **Ratings/finalisation** (`:353-421`).
5. **Reports** (`:423-425`) — `diagnostics.write_diagnosis`, `status_report.write_status`.

## Question‑by‑question

### Where are games generated?
`training/selfplay_core.py::run_generation` (`:177`) → `run_arena_inproc` (`:138`) →
`analytics.tournament.arena_runner.run_experiment`. Per‑game records land in
`training/state/selfplay_runs/gen<NNNN>/.../games.jsonl` (git‑ignored). Candidate
evaluation games are generated by `evaluate_candidate` (`:430`) over a rotating
battery built by `build_eval_arenas` (`:367`).

### Where is Elo calculated?
`analytics/tournament/elo.py::EloTracker`. The nightly seeds it from the SQLite
timeline (`_seed_elo_tracker`, `nightly_run.py:96`) and recomputes a fresh champion
Elo **per generation** by replaying that generation's games
(`_replay_run_dir_games`, `:433`; persisted at `:249`). Stored in
`training/state/ratings.sqlite` tables `rating_history`, `run_summary`, `game_elo`
(`training/ratings_db.py`).

### Where is TrueSkill calculated?
`analytics/tournament/trueskill_rating.py::TrueSkillTracker`, updated from each game via
`scripts.champion_loop.update_trueskill_from_run` (called in `run_generation`,
`selfplay_core.py:214`). Seeded/persisted through `build_tracker`/`persist_tracker`.

### How are candidates created?
`selfplay_core.build_candidate` (`:235`) dispatches to:
- `build_regression_candidate` (`:262`) — per‑phase linear regression of the
  accumulated snapshot CSV onto `final_score` via
  `scripts.champion_loop.refit_evaluator_weights` (`scripts/champion_loop.py:398`).
- `build_td_candidate` (`:279`) — loads TD‑learned weights from
  `training/state/td_evaluator_weights.json` (produced by `python -m training.td_learning`).

Both clone the champion and swap in `state_eval_phase_weights`. A candidate is the
champion **with different evaluator weights** — there is no separate model file.

### Why does the report say "No candidate was learned this cycle"?
The literal string is emitted by `training/status_report.py:141` and
`training/email_summary.py:210` whenever `eval_result is None` /
`candidate_params` is null. In the committed state this is true because the
candidate→eval phase has not executed since gen 1 (see diagnosis §2). The message is
deliberately vague — replacing it with a specific per‑approach reason is a core goal
of this work.

### Why did candidate evaluation not run?
`evaluate_candidate` runs only inside `if candidate_cfg is not None and
time.monotonic() < deadline` (`nightly_run.py:311`). The generation loop above it has
**no per‑generation cap** and consumes the budget (~23 min/generation in CI), so the
post‑loop candidate/eval/report tail is reached rarely or after the deadline. Evidence:
`training/status.md` and `training/reports/latest_diagnosis.md` are frozen at gen 1
while `latest.json` advanced to gen 102 — the report writers at `:424-425` (which run
after eval) have not executed since gen 1.

### What determines whether an agent is promoted?
`analytics/tournament/gauntlet.py::evaluate_promotion` (`:236`) with
`PromotionThresholds` (`:209`): all of (1) candidate ranked #1 by TrueSkill
conservative, (2) beats runner‑up head‑to‑head, (3) `Δμ ≥ min_mu_margin` (0.5),
(4) Wilson‑95 % win‑rate lower bound > 1/num_agents, (5) `n_seeds ≥ 2`,
(6) `total_games ≥ 40`. On pass, `nightly_run._promote` (`:608`) checkpoints the
outgoing champion, swaps params, resets sigma, updates `champion.json` + lineage.

### Is the Elo trajectory measuring strength or noise?
**Noise.** The champion config has not changed in 102 generations (see below), yet
`history.jsonl` shows `champion_elo` swinging 1260→1252→1227→1264→1288 over gens
98‑102 (±60) on only 12 games/generation against a rotating opponent set. With a fixed
agent, all movement is matchup/seed variance, not skill.

### Are agents evaluated against a stable benchmark pool?
No. Challengers rotate per generation via `select_challengers` (one of `MCTS_VARIANTS`
plus heuristic/random). The eval battery (`build_eval_arenas`) uses historical
checkpoints/variants. There is no fixed, versioned benchmark roster, so cross‑run Elo
deltas are not comparable.

### Is the champion actually changing between generations?
No. `latest.json`: `champion.version = "gen0"`, `checkpoints = []`,
`last_promoted_generation = null`. `champion.json` lineage has a single `gen0`
cold‑start entry. **Zero promotions in 102 generations.**

### Are checkpoints/artifacts saved correctly?
`training/state/checkpoints/` is empty (no promotions → no checkpoints). Durable state
(`latest.json`, `champion.json`, `ratings.sqlite`, `history.jsonl`) is saved atomically
and committed. There is no `training/artifacts/candidates/` directory — candidates are
never persisted as standalone artifacts. `data/td_trajectories.csv` (1,611 rows) and
`data/champion_snapshots.csv` (37,096 rows) exist and are healthy.

### Is the GitHub Actions time budget preventing useful training?
Partly. The 70/30 split plus an uncapped generation loop means the learning/eval/report
tail is starved (see "Why did candidate evaluation not run?"). The job itself completes
(state commits land), so the issue is **budget allocation inside the run**, not the
350‑minute CI cap.
